# DECISIONS.md

## v1.4.4 의사결정

| 결정 | 이유 | 상태 |
|---|---|---|
| 검출 결과를 `raw_evidence`, `object_candidates`, `objects`로 분리한다. | 야간/우천 영상에서 false positive가 최종 객체 목록을 오염시키는 문제를 줄이기 위해서다. | 결정 |
| 전조등과 밝은 영역은 객체가 아니라 evidence로 다룬다. | 밝은 영역은 차량, 가로등, 간판, 물방울, 노면 반사를 모두 포함할 수 있기 때문이다. | 결정 |
| `unknown`과 `motion_region`은 `objects`에 직접 넣지 않는다. | 불확실한 관측값을 최종 객체처럼 보이게 하면 Scene Vector 신뢰도가 떨어진다. | 결정 |
| YOLO 결과도 신뢰도와 약한 ROI 기준을 통과해야 확정 객체로 승격한다. | 모델 결과가 불안정할 때도 확정 객체 목록을 보수적으로 유지하기 위해서다. | 결정 |
| 2.5D 탑뷰에는 기본적으로 확정 `objects`만 표시한다. | raw evidence와 후보가 3D 객체처럼 해석되는 것을 막기 위해서다. | 결정 |
| SAM2 계열 모델은 v1.5 이후 후보 윤곽 정제와 접지점 보조 용도로 검토한다. | segmentation이 false positive 억제 구조를 대신할 수는 없기 때문이다. | 결정 |

## 초기 의사결정

| 결정 | 이유 | 상태 |
|---|---|---|
| 데모 v1 출력 형식은 JSON으로 한다. | AI 분석, 시각화, 저장, 비교가 쉬운 구조화 데이터가 필요하다. | 결정 |
| 데모 UI는 Streamlit을 사용한다. | 빠르게 업로드 UI와 JSON 확인 화면을 만들 수 있다. | 결정 |
| 주 언어는 Python으로 한다. | OpenCV, YOLO, 데이터 처리 생태계와 잘 맞는다. | 결정 |
| 객체 검출은 추후 Ultralytics YOLO 기반으로 연결한다. | 초기에는 구조 검증이 우선이며, YOLO는 교체 가능한 detector 모듈 안에 둔다. | 결정 |
| YOLO는 장기 핵심 구조가 아니라 detector backend 중 하나로 둔다. | 이후 segmentation, depth, tracking, vision-language 백엔드를 추가할 여지를 유지한다. | 결정 |
| 3D 좌표는 정밀 복원이 아니라 영상 기반 추정값이다. | 단일 블랙박스 영상만으로 실제 깊이를 정확히 알 수 없기 때문이다. | 결정 |
| z 좌표는 초기에는 도로면 기준 `0.0`으로 둔다. | 데모 v1은 도로 위 객체 중심이며 고도 복원은 다루지 않는다. | 결정 |
| 모든 위치 추정값에는 `confidence`와 `range`를 포함한다. | 추정값의 불확실성을 JSON 소비자가 함께 판단해야 한다. | 결정 |
| 공개 저장소에는 캐시, 로컬 데이터, 비밀 설정 파일을 커밋하지 않는다. | 블랙박스 영상과 로컬 환경 정보가 GitHub에 올라가지 않도록 해야 한다. | 결정 |
| AGENTS.md는 공개 가능한 프로젝트 작업 규칙 중심으로 유지한다. | 내부 실행 프롬프트보다 작업에 필요한 규칙만 담는 편이 안전하다. | 결정 |

## 버전별 의사결정

| 결정 | 이유 | 상태 |
|---|---|---|
| v1.1은 업로드 영상 기반 데모 분석을 연결한다. | 영상 저장, 프레임 추출, JSON 저장 흐름을 먼저 안정화한다. | 결정 |
| v1.1은 첫 번째 샘플 프레임 기준 `scene_vector.json`을 저장한다. | 프레임 시퀀스 분석과 추적은 다음 단계로 분리한다. | 결정 |
| v1.2는 Ultralytics YOLO를 데모용 실제 객체 검출 백엔드로 도입한다. | 실제 bbox와 class를 받아 Scene Vector 변환 흐름을 검증한다. | 결정 |
| v1.3은 추출된 모든 샘플 프레임에 detector를 적용한다. | 첫 프레임만 분석하면 영상 시퀀스 기반 확장성을 확인하기 어렵다. | 결정 |
| v1.3은 슬라이더로 샘플 프레임을 넘겨보는 UI를 사용한다. | 실시간 재생 전 단계에서 프레임별 결과를 안정적으로 검토할 수 있다. | 결정 |
| v1.3은 프레임별 결과 배열을 `scene_vectors.json`으로 저장한다. | 단일 `scene_vector.json`과 구분해 시퀀스 분석 결과를 보존해야 한다. | 결정 |
| v1.3에서는 객체 추적과 실제 움직임 벡터 추정을 아직 하지 않는다. | track ID 연속성과 속도 추정은 별도 단계로 다루는 편이 안전하다. | 결정 |
| v1.4는 야간 전조등/고휘도 후보를 별도 detection source로 보존한다. | 정면 차량이 형상보다 빛으로 보이는 야간 장면에서 YOLO 단독 누락을 줄인다. | 결정 |
| v1.4는 도로 ROI 기반 강한 필터링을 적용하지 않는다. | 검증 영상이 적은 상태에서 도로 위치 규칙을 강하게 넣으면 오탐 제거 실패가 커질 수 있다. | 결정 |
| v1.4는 이전 샘플 프레임의 고휘도 후보와 이어지는 경우 confidence를 보강한다. | 샘플링이 실제 프레임에 가까울수록 앞뒤 프레임 비교가 누락 방지 근거로 작동할 수 있다. | 결정 |
| 전조등 후보는 확정 객체가 아니며 `is_candidate`와 `detection_reason`을 함께 기록한다. | 차량이라고 단정하지 않으면서 위험 가능성이 있는 unknown 객체를 Scene Vector에 남기기 위해서다. | 결정 |
| v1.4.1은 단일 고휘도 후보를 더 엄격하게 필터링한다. | 가로등, 단순 빛번짐, 앞유리 물방울 잔상은 차량 후보가 아니므로 형태, 크기, 위치 기준으로 오탐을 줄인다. | 결정 |
| v1.4.1은 2.5D 탑뷰 박스에 객체 타입별 기본 물리 크기를 사용한다. | 고정 크기 마커는 차량, 버스, 사람, 전조등 후보의 크기 차이를 표현하지 못한다. | 결정 |
| bbox 픽셀 면적은 탑뷰 박스 크기에 약하게만 반영한다. | 화면상 bbox 크기는 실제 물리 크기가 아니라 거리와 촬영 조건의 영향을 크게 받기 때문이다. | 결정 |
| v1.4.2는 제외된 광원/반사를 Scene Vector 객체로 저장하지 않는다. | 보닛 반사, 상단 가로등, 간판, 물방울 잔상이 객체 JSON에 들어가지 않도록 해야 한다. | 결정 |
| v1.4.2는 제외 이유를 앱 진단 정보로 표시한다. | 어떤 기준으로 후보를 제거했는지 확인할 수 있어야 튜닝 속도가 빨라진다. | 결정 |
| v1.4.3은 SAM2 도입 전에 OpenCV 프레임 차분 기반 움직임 보조 검증을 먼저 추가한다. | YOLO와 고휘도 후보만으로는 야간/우천 장면의 누락과 오탐을 동시에 다루기 어렵기 때문에 시간축 변화량을 별도 근거로 사용한다. | 결정 |
| `motion_flow`는 객체 확정 근거가 아니라 보조 근거로 기록한다. | 프레임 차분은 카메라 흔들림, 노면 반사, 와이퍼/물방울 변화에도 반응하므로 실제 객체 판정과 구분해야 한다. | 결정 |
| 기존 후보와 겹치지 않는 움직임 영역은 `unknown/motion_region` 후보로 보존할 수 있다. | 차량 형상이 보이지 않더라도 움직임이 있는 영역을 완전히 버리지 않아 후속 검증과 모델 개선 데이터로 사용할 수 있다. | 결정 |
| SAM2 계열 segmentation 백엔드는 v1.5에서 별도 단계로 검토한다. | v1.4.3은 YOLO 보조 휴리스틱의 한계를 확인하는 단계로 두고, 모델 의존성이 큰 segmentation 도입은 다음 버전으로 분리한다. | 결정 |
